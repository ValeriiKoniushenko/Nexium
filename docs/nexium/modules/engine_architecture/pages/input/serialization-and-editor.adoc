= Serialization and the Binding Editor
:toc:
:toclevels: 3

Binding configuration is persistent. Accepted presses, action pulses, callbacks,
router ownership, and actor possession are runtime relationships.
Editing or restoring configuration invalidates old action state rather than
reinterpreting a held key under a new binding.

== What is saved and copied

[cols="3,2,2,4",options="header"]
|===
|State |Serialized |Copied to clone |Notes
|Binding vector
|Yes |Yes
|Reflected legacy field name `_bindings` is retained.
|Input context
|Yes |Yes
|Reflected `_inputContext` field.
|speed / mouseSensitivity
|Yes |Yes
|Defaults 600 / 0.5; consumer settings, not core input scaling.
|Explicit input-enabled flag
|No |Yes
|Set through setInputEnabled; distinct from reflected BaseComponent state.
|Accepted/held/transient actions
|No |No
|A fresh runtime starts inactive.
|Action callbacks / delegate listeners
|No |No
|Reinstall behavior during initialization.
|Router registration / gesture ownership / blocked buttons
|No |No
|Established by live lifecycle/routing.
|Possessed Actor
|No |No
|GameController restores possession explicitly at runtime.
|===

BaseComponent's own serialized fields/child tree remain governed by the component
serialization contract. InputMap is a configuration value, not a separate ECS asset type.
`getInputMap()` returns a copy; `setInputMap()` copies its bindings into the component.

.Editor changes configuration; runtime state is rebuilt through fresh input.

== Binding JSON contract

The custom `to_json/from_json` adapters for InputBinding live in InputMap.cpp.
They preserve the keyboard-oriented legacy shape while adding mouse and pointer sources.

[cols="2,4",options="header"]
|===
|Field |Representation
|action
|StringAtom's JSON name; interned on input.
|triggerKey
|Keyboard enum name as a string, or an object with device = Mouse and button = the mouse enum name.
|requiredKeys
|Array of the same keyboard-string/mouse-object button representations.
|trigger
|OnPress, WhileHeld, or OnRelease string.
|source
|Omitted for Button; PointerMove or Wheel for nonbutton bindings.
|===

=== Compatibility on read

The adapter accepts:

* `triggerKey`, falling back to the older `key` field if triggerKey is absent.
* Keyboard names and older integer keyboard codes.
* Mouse objects with a recognized Mouse device/button name.
* Legacy `requiredModifiers` bits, converted into required Left Control, Shift, Alt,
  and Super keys, without duplicating identical stored physical keys.

Source defaults to Button. Unrecognized source strings remain Button.
Trigger defaults to OnPress; unrecognized trigger strings also become OnPress.
Unrecognized buttons are ignored, leaving an absent trigger as None.
Button entries with None triggers remain editable but cannot resolve.

This is not a promise that arbitrary malformed JSON is accepted: incorrect field
types can still cause JSON conversion errors. Loading is compatibility handling,
not a general migration/error-repair framework.

== Mutation and runtime invalidation

[cols="3,5",options="header"]
|===
|Operation |Runtime effect
|Valid bind, including replacement
|Cancel all current action state and refresh routing.
|Invalid bind
|Return false without changing configuration or runtime.
|unbind when an action exists
|Remove all its entries, cancel all runtime state, refresh.
|unbind when absent
|Return false without cancellation.
|clearBindings
|Cancel, clear vector, refresh; handlers remain.
|setBindings / setInputMap
|Copy vector, cancel all runtime state, refresh, preserve handlers.
|Different input context
|Cancel all state and refresh in the new context.
|Same input context
|No change.
|Changed explicit input-enabled flag
|Cancel and refresh.
|Same explicit input-enabled flag
|No change.
|setActionCallback
|Change the handler independently; do not replace bindings.
|Post-deserialization
|Cancel stale state and refresh routing.
|===

Even `setBindings(getBindings())` cancels accepted holds. Its local copy makes
self-aliasing safe, but equality is not checked to preserve active state.

== Opening the editor

The ECS InputController adapter shows an Input shortcuts section and an Edit
shortcuts button. That opens InputBindingsEditor for the selected input component.
The editor presents a binding list and settings for action name, recorded chord,
and trigger. Add creates a named Button entry with a None trigger; it becomes
usable after a valid chord is supplied. Delete removes the selected vector entry.

Edits apply through setBindings and mark the owning asset editor dirty.
This means editing live bindings also resets their action runtime.
The current settings widget is not a general editor for PointerMove/Wheel source
selection or all input-device features.

Action renaming does not rename callback registrations. Handlers are keyed by the
original action atom; the renamed action needs a corresponding handler/consumer.
Temporarily removing a binding does not erase its old callback.

== Save and target lifetime

InputBindingsEditor tracks the target component and owner weakly, and retains
the target asset when opened from an asset editor.
If the original window closes but the retained asset still owns the component,
the bindings window can continue editing and save that asset directly.

If there is no retained valid asset and the owner/target no longer matches, the
window clears its target. Switching targets, selection, or binding sessions cancels
recording. Closing the bindings window clears target state.

Save routes through the matching asset editor when available, otherwise directly
through the retained asset. Save is disabled during active recording capture,
including its pending-release fence.
Editing and saving are separate: a live setBindings update is not by itself a
filesystem save.

== Binding recording

.Recording suppresses actions until every recorded physical hold has ended.
image::input-recording-capture.svg[Capture guard lifetime and pending physical release fence]

The widget starts an InputCapture guard and subscribes to raw Platform keyboard,
mouse, and focus events. Routed actions are suppressed, while the recorder sees
buttons needed to build a chord.

Keyboard modifiers are normalized and recorded as requirements. The most recently
recorded non-modifier/button becomes the trigger, with the other currently tracked
buttons as requirements.
Mouse presses are recorded only in the widget's capture area, so clicking Confirm
or Cancel is not interpreted as the intended mouse shortcut.

Confirm requires a non-None trigger and applies the recorded chord. Cancel leaves
the existing chord unchanged. Focus loss requests cancellation, and invisible/closed
recording UI releases its recording state/subscriptions.

When the guard ends, InputCapture's shared release fence continues suppressing
actions until all tracked held buttons are released. The final fence-clearing
Release is suppressed too. This avoids immediately executing the shortcut just
recorded or confirmed.

Focus loss/reset clears the held-button fence. A still-live capture guard keeps
suppression active until it is destroyed.

== Persistence and initialization rules

Use reflected configuration for editable state, and install behavior at runtime.
Do not serialize lambdas, delegates, intrusive runtime registrations, or weak
possession as binding configuration.

For defaults, preserve restored maps. The spectator's empty-vector convention is
one policy, not a universal serialization rule. Games needing versioned defaults
or intentionally empty persisted maps should track that decision explicitly.

JRM-generated files update through CodeGenerator in the normal build. Source tags
used by these docs are comments in the real source/tests; the Antora examples
family links to those files instead of storing duplicate snippets.
