[[engine-architecture]]
= Architecture and Migration Review
:page-aliases: draft--new-architecture.adoc

This assessment separates implemented boundaries from proposed work.
The current executable combines the example game and 2D editor; 3D is optional.

== Layer map

The xref:module-graph.adoc[source layers and target map] describe the implemented eight-layer structure.
Keep it.
Focused Fundamental/Subsystem libraries and Runtime's interface-based editor integration are useful boundaries.
New folders and framework names alone do not complete the migration.

== Build modules

CMake now centralizes target settings, declares most source lists explicitly,
and compiles JRM separately in Release.
The adapter uses the engine toolchain.
Public-header verification and executable layer consumers make interfaces reviewable.

See xref:build:cmake-structure.adoc[CMake infrastructure] for real options and checks.
Tests and benchmarks are disabled by default. CI enables tests in GCC and Clang Debug builds
with 3D off, and adds format, tidy, coverage, and Valgrind checks; see
xref:build:ci-cd.adoc[CI coverage]. No Release, 3D, or benchmark job is configured.

== Object model and ownership

GameInstance owns World and SceneManager as siblings, alongside assets and UI.
Runtime borrows GameInstance; EditorIntegration borrows Runtime and owns editor tools.
World carries time, lighting, framework state, the start-scene name, and an observed camera.
SceneManager owns every scene, opens and closes them, and activates the current one in World.
Scene owns root component trees and handles persistence and drawing.

The model is suitable for a small authoring engine.
World does not yet provide the ownership/lifetime boundary implied by its UE-style name.
Most new managers and GameInstanceSubsystem have logging scaffolding without operational contracts.
Input is the exception that proves the point: `InputSystem` is a real routing service with
contexts, controllers, and tests, but it is a global singleton rather than something a session
owns — so switching worlds or sessions has no defined effect on it.

== Reflection and persistence

Keep JRM and the existing reflected component model.
Component macros perform self-registration through static initializers.
The serialized “Blueprint” assets are component templates.

Keep scene versioning, reconstruction before root replacement, atomic saves,
failed-load autosave protection, and the rule that a scene touches only a file it loaded or wrote.
Define generic instance overrides, asset moves/references, stable object identity,
and caller-visible save errors before relying on the editor for larger authored games.

== Migration boundaries

Prioritize these behaviors within the existing modules:

. Decouple gameplay ticking from camera presence; define simulation state and time.
. Finish world/scene replacement invalidation: switching scenes already restores each scene's
  camera and clears selection, but component subscriptions are not invalidated.
. Introduce editor commands, undo/redo, dirty documents, and accurate save results.
. Create a disposable Play-session copy from authored state and destroy it on Stop.
. Add an asset-reference/move policy and portable content identifiers.
. Extend executable interface checks and CI to the World/Runtime/editor boundary.
. Retire the polled `InputAction` managers once mouse events route through `InputSystem`,
  so input has one path and one context policy.

A project-content context should move game-specific atlas setup into game-example.
Keep the editor-enabled executable while building these contracts.
Game-only packaging is not implemented.
