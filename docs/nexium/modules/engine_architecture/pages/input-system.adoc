= Input System

The input system is mid-redesign. Platform now turns every GLFW callback into a small typed
event, and `NX::InputSystem` collects those events into a per-frame queue. The layer that
is meant to consume the queue — controllers, bindings, and input contexts — has been removed
and not yet replaced, so gameplay and editor code currently read input by polling.

[cols="2,3,3",options="header"]
|===
|Layer |Where |State
|Typed events |`Platform/Input/Events` |Live. Produced for keyboard, mouse, gamepad, and window focus/iconify changes.
|Window delegates |`Platform::Window` |Live. One delegate per event kind; anything may subscribe.
|Gamepad polling |`Platform::Joystick` |Live. Polled once per frame, reports changes as events.
|Event queue |`NX::InputSystem` (NxWorld) |Live as a queue. Its per-type handlers are empty: nothing is routed yet.
|Polled actions |`NxSubsystems/Input` |Live. The only path that drives behavior today.
|Controllers, chords, contexts |`NxWorld/Framework/InputController.h` |Disabled. See <<disabled>>.
|===

New code that needs input right now should either subscribe to a `Platform::Window`
delegate (event-driven) or use the polled actions. Do not build on `InputController`,
`KeyChord`, or `InputContext`: they are commented out.

== Events

Every event derives from `NX::InputEvent`, which carries three things: an `EventType`, an
`InputDeviceType`, and an `InputDeviceId`. The base is deliberately non-polymorphic — its
destructor and copy operations are protected, so an event can be neither destroyed nor
copied through a base reference. Events are plain values.

[cols="2,2,4",options="header"]
|===
|Event |Device |Payload
|`KeyboardEvent` |Keyboard |Key, `InputState`, scancode, `InputModifier` mask.
|`TextInputEvent` |Keyboard |Unicode codepoint.
|`MouseMoveEvent` |Mouse |Cursor position and delta since the previous sample.
|`MouseButtonEvent` |Mouse |Button, `InputState`, modifiers, and the cursor position at the moment of the click.
|`MouseScrollEvent` |Mouse |Scroll offset on both axes.
|`MouseEnterEvent` |Mouse |Whether the cursor entered or left the window.
|`GamepadButtonEvent` |Gamepad |Button and `InputState`.
|`GamepadAxisEvent` |Gamepad |Axis index and value.
|`GamepadConnectionEvent` |Gamepad |Connected or disconnected.
|`WindowFocusEvent` |None |Focused or not.
|`WindowIconifyEvent` |None |Iconified or not.
|`WindowResizeEvent` |None |Window size and framebuffer size. Declared, not produced yet.
|`WindowCloseEvent` |None |No payload. Declared, not produced yet.
|===

The shared vocabulary lives in `Events/InputEvent.h`:

* `InputState` is `None`, `Pressed`, `Released`, or `Repeated`. It is platform-independent:
  backends convert their native values explicitly, and `None` is distinct from `Released`.
* `InputModifier` is a bitmask of Shift, Control, Alt, Super, CapsLock, and NumLock, with
  `|` and `&` operators.
* `InputButton` wraps a 16-bit index — a keyboard key code, a mouse button, or a gamepad
  button, depending on the event that carries it. A default-constructed button is invalid
  (`isValid()` is false).
* `InputDeviceId` identifies the device. `0` is `InvalidInputDeviceId`; keyboard and mouse
  events currently leave it at `0`, and gamepads use the GLFW joystick index plus one.

`AnyInputEvent` is a `std::variant` over all event types, and it is what the queue stores:

[source,cpp]
----
include::example$any-input-event.h[tag=input_any_event,indent=0]

The two assertions are the contract for adding an event: it must keep the variant within 32
bytes and trivially copyable. The `InputEventType` concept is satisfied by exactly the
variant's alternatives, and `InputSystem` declares one `handle()` overload per alternative,
so a new event type fails to compile until it is handled.

== Platform layer

`Platform::Window` installs the GLFW callbacks, builds the matching event, and triggers a
delegate. GLFW constants do not leave Platform: `Platform::ToInputState()` and
`Platform::ToInputModifiers()` in `Platform/Input/Glfw.h` convert actions and modifier bits,
and an unknown action maps to `InputState::None`.

[cols="3,3,2",options="header"]
|===
|Delegate |Argument |Queued by InputSystem
|`onKeyPressed` |`KeyboardEvent` |Yes
|`onMouseMove` |`MouseMoveEvent` |Yes
|`onMouseKeyPressed` |`MouseButtonEvent` |Yes
|`onMouseWheel` |`MouseScrollEvent` |Yes
|`onFocusChanged` |`WindowFocusEvent` |Yes
|`onJoystickConnected` |`GamepadConnectionEvent` |Yes
|`onJoystickButtonPressed` |`GamepadButtonEvent` |Yes
|`onJoystickAxisChanged` |`GamepadAxisEvent` |Yes
|`onTextInput` |`TextInputEvent` |No
|`onCursorEntered` |`MouseEnterEvent` |No
|`onIconifyChanged` |`WindowIconifyEvent` |No
|`onResize`, `onFramebufferResize` |`Core::ISize2` |No; these do not use `WindowResizeEvent`.
|===

Delegates fire synchronously inside the GLFW callback, during `Window::pollEvent()`. A
subscriber therefore sees an event before the queue is processed.

`Window` also keeps its own state from these events: `isFocused()`, `isIconified()`, and the
global drag-and-drop tracker `gDragDrop`, which starts on a button press at the event's
position and becomes a drag after the cursor moves 15 pixels.

=== Click position

`MouseButtonEvent::getPosition()` is the cursor position sampled in the button callback.
Use it rather than the current cursor position: by the time a queued click is handled the
mouse may have moved.

=== Cursor delta

`MouseMoveEvent::getDelta()` comes from a `CursorDeltaTracker` owned by the window, not
from static state. The first sample after a reset has a zero delta, which removes the jump
that would otherwise follow a discontinuity:

[cols="3,3",options="header"]
|===
|Trigger |Effect
|Focus gained or lost |Tracker reset; next move reports zero delta.
|Cursor enters or leaves the window |Tracker reset.
|`Window::setCursorMode()` |Tracker reset.
|`Window::setCursorPosition()` |Tracker re-based to the new position, so the warp is not reported as movement.
|===

== Gamepads

`Platform::Joystick` is a static class polled once per frame, right after the window events.
It supports only devices GLFW recognizes as standard gamepads; any other joystick is treated
as disconnected. Its events go out through the window's joystick delegates, with
`InputDeviceId` set to the GLFW joystick index plus one.

* *Connection.* A newly seen gamepad has its state reset and then reports
  `GamepadConnectionEvent(connected = true)`.
* *Buttons.* A `GamepadButtonEvent` is sent only when a button changes: `Pressed` or
  `Released`. There is no `Repeated` state for gamepad buttons.
* *Axes.* A `GamepadAxisEvent` is sent when the value differs from the *last reported* value
  by more than the threshold (`0.01` by default; `setAxisChangeThreshold()` clamps to
  `[0, 2]`). Comparing against the last reported value means slow drift still produces an
  event once it accumulates.
* *Rest values.* Sticks rest at `0`, triggers at `-1` (`getAxisRestValue()`).
* *Disconnection.* Before reporting `connected = false`, the class releases every button
  that was held and returns every axis that is off its rest value. A consumer never keeps a
  stuck button or axis from a device that went away.

`isConnected()`, `isButtonPressed()`, and `getAxis()` expose the current state for polling.
`Joystick::GamepadButton` and `Joystick::GamepadAxis` name the standard layout.

== InputSystem: the event queue

`GetInputSystem()` is a `Core::Singleton`. `GameInstance::initialize()` calls
`initialize(window)`, which subscribes to the delegates marked _Yes_ above and copies each
event into the queue with `queueEvent()`. `queueEvent()` is public and constrained by
`InputEventType`, so tests and tools can inject events without a window.

----

----

The contract of the queue:

* Events are stored by value in arrival order, across device types.
* Two buffers are swapped each frame, so both keep their capacity and a steady-state frame
  does not allocate.
* An event queued while the queue is being processed lands in the next frame.
* Losing window focus does not drop queued events. GLFW synthesizes key releases after the
  focus callback, and they are queued after the presses they belong to.
* `resetInput()` discards everything pending.

----
include::example$input-events-tests.cpp[tag=input_queue_order,indent=0]
----

`getPendingEvents()` and `getPendingEventCount()` expose the queue before it is processed.
The thirteen `handle()` overloads are the single entry point per event type and are currently
empty. Processing a frame's events therefore has no observable effect yet.

== Polled input

`Platform::Keyboard` and `Platform::Mouse` (now under `Platform/Input/InputDevices`) answer
"is this key down right now" straight from GLFW. `game-example/Player` uses that directly:
W/A/S/D or the arrow keys.

`KeyboardInputManger` and `MouseInputManger` build named actions on top. They own intrusive
action references indexed by `Core::StringAtom` names; "Manger" is the current API spelling.
`getOrCreate()` reuses the existing name; it does not change that action's key binding.

`InputAction::update()` polls its key, applies repeat/frequency limits, snapshots left
Shift/Alt/Ctrl as `InputState` values, and passes that snapshot to `onPress`.
`SpecKeysState::isNothingPressed()` is true when none of the three is `Pressed`.
Repeat defaults to enabled with zero delay. Disable repeat for one notification per press;
frequency limits use elapsed `system_clock` milliseconds.

Mouse actions also provide:

* `onMouseClick`: current position on a qualifying press, using the same repeat policy.
* `onMove`: position delta after the first sample establishes a baseline.
* `onDrag`: position delta while Platform reports dragging and the action's button condition matches.

A mouse click here is a press notification, not release detection.
`MouseInputManger::onWheel` forwards the offset of the window's `MouseScrollEvent`.

[cols="2,4",options="header"]
|===
|Owner |Update path
|GameEditor |Keyboard and mouse mappings after drawing editor windows.
|EditorIntegration in GameOnly mode |Editor keyboard mappings only.
|Spectator |Its own keyboard and mouse mappings during its scene tick.
|`NxECSBasedEditor` |Its own keyboard manager for the Delete shortcut inside component editors.
|===

Nothing filters polled input by focus or context. A shortcut that must not fire during
gameplay has to check focus itself — as the Delete shortcut does with
`isApplicationViewportFocused()`.

== Disabled during the redesign

The previous routing layer is commented out in place rather than deleted, and the code that
depended on it is switched off with it:

[cols="2,4",options="header"]
|===
|What |Current state
|`NX::InputController`, `KeyChord`, `InputContext`, `InputActionEvent` |Commented out in `NxWorld/Framework/InputController.{h,cpp}` and `NxSubsystems/Input/InputTypes.{h,cpp}`.
|Context switching in the frame loop |`setActiveContext()` call is commented out; the system has no notion of Editor versus Gameplay input.
|Right-to-left modifier normalization |Gone with the old dispatch. `KeyboardEvent` reports the key GLFW reported.
|Editor binding editor |`ECSEditorInputControllerAdapter` is commented out and no longer registered in `NxECSBasedEditor`.
|Editor "Save all" chord |Not bound.
|`Spectator3D` keyboard movement and wheel dolly |Commented out. Right-drag look still works through the polled mouse action.
|`tests/ECSTests/InputControllerTests.cpp` |Wrapped in `#if 0` until the tests are ported.
|===

`NxWorld/Framework/Input/InputController.h` holds the start of the replacement in namespace
`NxWorld::Framework::Input`: `InputDevice`, `KeyChord`, `Binding`, and an empty
`InputController` component. It is a sketch — not reflected, not registered, and not built.

Implementation: `Platform/Input/Events/*.h`, `Platform/Input/{Window,Glfw,CursorDeltaTracker}.*`,
`Platform/Input/InputDevices/{Keyboard,Mouse,Joystick}.{h,cpp}`,
`NxWorld/Framework/InputSystem.{h,cpp}`,
`NxSubsystems/Input/{InputAction,InputManager}.{h,cpp}`,
`Editor/GameEditor.cpp`, and `NxWorld/Scene/SceneObjects/Spectator/Spectator.cpp`.
