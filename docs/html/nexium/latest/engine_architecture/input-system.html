ECS Input Routing

Purpose

The input routing system converts raw keyboard events into named ECS actions such as Move forward, Save game, or Open inventory. Gameplay code depends on those semantic names instead of polling hardware keys directly.

The system is designed to solve three related problems:

  • the same shortcut may have different meanings in different parts of the application;

  • an active UI or gameplay context must be able to consume input before lower contexts receive it;

  • input configuration must be serializable and editable without creating bindings in gameplay code.

For example, both gameplay and an inventory may bind Ctrl + S. While the inventory is active, it receives and consumes the shortcut. After the inventory is deactivated, the same shortcut reaches gameplay again.

The current router handles keyboard input. Existing mouse actions still use the older mouse input APIs.

System at a glance

Window keyboard callback
        |
        v
Internal::InputSystem
  - queues raw events
  - tracks held keys
  - orders active controllers
  - routes until Consumed
        |
        v
InputController ECS components
  - match KeyChord bindings
  - maintain named action state
  - emit semantic action events
        |
        v
Gameplay code
  - polls isActionPressed("Move forward")
  - or subscribes to onAction

There are two distinct responsibilities:

Internal::InputSystem

Engine-owned infrastructure. It receives window events and decides which controller gets each event. Gameplay code should not access it.

InputController

A serializable ECS component. It owns bindings and exposes named actions to gameplay code.

Core concepts

Binding

A binding associates a semantic action with a keyboard chord and an activation mode.

struct Binding
{
    StringAtom action;
    KeyChord chord;
    InputActionTrigger trigger;
};

The action name is the contract between data and gameplay code. Changing the physical shortcut does not require changing gameplay logic.

Key chord

A chord consists of one trigger key and zero or more required keys.

KeyChord{
    .triggerKey = Keyboard::Key::B,
    .requiredKeys = {
        Keyboard::Key::Left_Control,
        Keyboard::Key::A
    }
};

This represents Ctrl + A + B. The required keys must already be held when the trigger key is pressed.

The trigger key makes the activation moment unambiguous. In Ctrl + A + B, pressing B starts the action; pressing only Ctrl + A does not.

Left and right versions of Ctrl, Shift, Alt, and Super are normalized by the engine, so a recorded modifier is not tied to one physical side of the keyboard.

Additional held keys do not invalidate a chord. Conflict resolution therefore considers a chord with more required keys more specific.

Activation modes

InputActionTrigger defines the value returned by isActionPressed():

Mode Action state Typical use

WhileHeld

true from chord activation until any chord key is released.

Movement, sprinting, camera controls.

OnPress

true for one input frame when the trigger key is pressed.

Jump, fire, open a menu, save.

OnRelease

true for one input frame when any active chord key is released.

Charged actions, confirmation on release.

One-frame actions are reset at the beginning of the next input frame. They can therefore be consumed through the same polling API as held actions.

The onAction delegate fires when the configured mode activates:

  • WhileHeld and OnPress fire on the initial press;

  • OnRelease fires on release;

  • operating-system key-repeat events do not fire the action again.

Frame lifecycle

GameInstance initializes the router after creating the window. Every game-loop iteration polls the window and then processes queued input:

Window::pollEvent();
Internal::GetInputSystem().processEvents();

One input frame performs the following work:

  1. Remove expired weak references to destroyed controllers.

  2. Clear OnPress and OnRelease actions left active from the previous frame.

  3. Detect controller activation and deactivation transitions.

  4. Dispatch every queued key event in order.

  5. Leave the resulting action state available for the gameplay tick.

Window callbacks only enqueue events. They do not execute gameplay logic immediately, which keeps input state changes aligned with the game loop.

Routing and conflict resolution

Only effectively active controllers participate in routing. A controller is effectively active when all of the following are true:

isEnabled()
&& inputActive
&& (!activationPredicate || activationPredicate())

For a key press, active controllers are ordered by these rules:

  1. A controller using BlockKeyboard is checked before passthrough controllers.

  2. Among passthrough controllers, a matching chord is checked before a non-matching controller.

  3. The matching chord with more required keys is checked first.

  4. Equal shortcuts are ordered by activation recency; the most recently activated controller wins.

There are no public numeric priorities. Activation order is assigned internally and cannot become a collection of unrelated magic numbers.

When a controller handles a matching binding, it returns Consumed and routing stops. If it returns Ignored, the next controller is checked.

Specificity example

Assume these bindings are active:

Spectator: S
Editor:    Ctrl + Shift + S

For Ctrl + Shift + S, both chords can technically match because additional held keys are allowed. The editor chord has two required keys and is therefore more specific, so it is routed first. The spectator never sees the consumed event.

Context example

Assume gameplay and an inventory both bind Ctrl + S. The inventory is activated after gameplay when it opens. Their chords have equal specificity, so activation recency routes the shortcut to the inventory.

inventoryInput->setInputActive(true);  // becomes the newest active controller
// Ctrl + S is handled by the inventory

inventoryInput->setInputActive(false);
// Ctrl + S can reach gameplay again

For modal contexts that must suppress all lower keyboard input, use:

modalInput->setBlockingPolicy(InputBlockingPolicy::BlockKeyboard);

BlockKeyboard consumes even keys for which that controller has no binding. Use it for pause menus and true modal dialogs, not for ordinary passthrough UI.

Configuring an InputController in the editor

Add an InputController as an ECS child of the object that owns the input configuration. For example, the base spectator asset contains both a camera and an input controller.

The Input Controller adapter displays every binding in the asset editor.

  1. Enter a semantic action name, for example Move forward.

  2. Press Record.

  3. Press the desired keys in order, for example Ctrl, A, then B.

  4. Verify the displayed Ctrl + A + B chord.

  5. Select While held, On press, or On release.

  6. Press Apply.

  7. Save the asset.

Recorded keys do not need to remain held simultaneously while editing. The recorder accumulates unique keys. The last ordinary, non-modifier key becomes the trigger key; preceding keys become required keys.

Bindings are serialized with the component:

{
    "action": "Move forward",
    "requiredKeys": [],
    "trigger": "WhileHeld",
    "triggerKey": "W"
}

The deserializer also understands the previous key and requiredModifiers fields so existing assets can migrate forward. Newly saved assets use only the current representation.

Using actions from gameplay code

Gameplay code locates the ECS controller and works with action names. It does not recreate editor-authored shortcuts.

auto spectator = gameScene.gerFirstOf<Spectator>();
auto* input = spectator ? spectator->findFirstChildOf<InputController>() : nullptr;

if (!input)
{
    errorLog("InputController was not found under Spectator.");
    return;
}

Polling action state

Polling is appropriate for continuous gameplay behaviour and also supports one-frame actions:

if (input->isActionPressed("Move forward"_atom))
    spectator->moveForward(-spectator->speed * delta);

The current modifier snapshot can affect behaviour without changing the binding:

const bool shift = (input->getActionModifiers("Move forward"_atom)
                    & InputModifier::Shift) != InputModifier::None;

Subscribing to actions

Delegates are useful for command-style actions:

subscriptions << input->onAction->subscribeAndGetID(
    [](const InputActionEvent& event)
    {
        if (event.action == "Save game"_atom)
            saveGame();
    });

Do not use both polling and a delegate to perform the same command unless two executions are intentional.

Runtime activation conditions

setInputActive() is the explicit on/off switch for a controller. An activation predicate adds a runtime condition without changing serialized data.

The spectator uses a predicate so its input works in game-only mode or while the game viewport is focused:

input->setActivationPredicate(
    [this]
    {
        if (renderMode == RenderMode::GameOnly)
            return true;

        const auto* viewport = gameEditor.getWindow<GameViewportEWC>();
        return viewport && viewport->isFocused();
    });

When the predicate changes from false to true, the controller becomes the newest active controller automatically. When it changes from true to false, held and transient actions are cleared to prevent stuck input.

Ownership and release handling

After a controller consumes a trigger-key press, the router records that controller as the key owner. Operating-system repeat events for that trigger key return to the same controller instead of being routed again.

Release events are offered to registered controllers because an action must end when any member of its chord is released, not only its trigger key. For example, releasing Ctrl, A, or B ends an active Ctrl + A + B chord.

Controllers are stored as weak pointers. The router does not extend ECS component lifetimes, and expired entries are removed before event processing.

Public and internal boundaries

Gameplay-facing code should use:

  • InputController;

  • Binding and KeyChord;

  • isActionPressed() and getActionModifiers();

  • onAction;

  • setInputActive(), setActivationPredicate(), and setBlockingPolicy().

Gameplay-facing code should not use:

  • Internal::InputSystem;

  • activation-order counters;

  • raw event queues or key-owner maps.

Those details belong to the engine and may change without changing the gameplay API.

Expected usage rules

  • Prefer semantic action names over direct keyboard polling in gameplay systems.

  • Configure reusable bindings in ECS assets rather than recreating them in code.

  • Use WhileHeld for continuous behaviour and OnPress or OnRelease for one-frame commands.

  • Use activation state or predicates to represent focus and open/closed contexts.

  • Use Passthrough by default; reserve BlockKeyboard for truly modal contexts.

  • Do not introduce numeric input priorities. Specificity and activation recency resolve conflicts automatically.
